Harnery describes a session with two independent state axes.

For a concise explanation you can share, start with the
[Session state feature page](/features/session-state/). To apply the same model
to Claude Desktop, use the
[session-management guide](/guides/manage-claude-desktop-sessions/).

| Axis | Values | Question answered |
| --- | --- | --- |
| `activity` | `unknown`, `working`, `needs_input`, `idle` | What is the agent doing now? |
| `task_state` | `active`, `blocked`, `done` | Is the declared task still open? |

The separation matters. An agent waiting for approval can have
`activity: needs_input` and `task_state: active`. After the turn ends, it can
be `idle` while the task remains `active`. Neither state implies the other.

## Activity evidence

Harnery changes activity only when a canonical event supplies evidence.

| Canonical event | Activity | Notes |
| --- | --- | --- |
| `session.started`, `session.resumed`, `agent.started` | `idle` | The session exists, but no open turn is implied. |
| `turn.started`, `tool.requested` | `working` | A turn or tool action is in progress. |
| `command.started` | `working` | Applied only during an already evidenced open turn. |
| `wait.started` | `needs_input` | The adapter directly reported an operator prompt. |
| `wait.ended` | `working` | The reported wait ended and execution resumed. |
| `turn.completed`, `session.ended`, `agent.completed` | `idle` | The current execution window ended. |

Output chunks, post-tool events, narration, unrelated coordination commands,
and elapsed time do not clear `needs_input`. New progress evidence or a stop
event does.

Codex provides a `PermissionRequest` hook, which Harnery records as
`wait.started`. Claude Code and Cursor sessions still use
`unknown` when their available events cannot prove an input wait. Harnery does
not turn a nearby pre-execution event into approval evidence.

## Lifecycle evidence

Only `coord.lifecycle_changed` changes task lifecycle. Stopping a process or reaching
the end of a turn does not mark the task `done`.

Human-facing sessions declare lifecycle explicitly:

```bash
harn agents lifecycle active
harn agents lifecycle blocked --reason "waiting for repository access"
harn agents lifecycle done --reason "implementation and verification complete"
```

`blocked` requires a reason. Leaving `blocked` clears that reason. Repeating
the same state and reason records nothing, which keeps replay idempotent.
Subagents, transient processes, and workflow children cannot make these
operator-facing declarations.

`done` also requires a current task and a passing Git finalization check. The
check covers the session's durable write-claim history, dirty touched paths,
enclosing submodule pointers, repository verification, and remote reachability.
After that check passes, `done` refuses while the session still holds file
claims; `agents release-claim --all` drops them without erasing claim history.
A refusal writes no lifecycle event and leaves the heartbeat unchanged. This
gate certifies repository hygiene, not tests or business correctness.

The per-turn `agents set-task` command remains lifecycle-neutral. Changing task
text while blocked or done returns a warning, but it does not reopen the task.
Use `lifecycle active` to resume explicitly.

The compatibility default is `active` when an older heartbeat or event stream
has no lifecycle event. A blocked state may carry a reason. Reopening the task
clears an obsolete blocker reason.

## Session finalization

Task lifecycle and session lifecycle are separate. `lifecycle done` says the
declared task is complete; `agents end` records terminal authority for the V3
session. A completed response (`turn.completed`) ends only one response.

Native harness callbacks remain the strongest end signal. When a harness lacks
one, Harnery can approve an explicit end, wait through a reversible archive
grace period, or reconcile idle, parent/run completion, stale, superseded, and
host-loss observations. Every path converges on one leased finalizer, so a
generation receives at most one terminal event and cannot be resurrected.

An agent can request its own end from the closing status command even though
that command still belongs to an open tool span and turn. Harnery persists the
intent, waits for the matching `tool.completed` and `turn.completed`, then lets
the stop hook record `session.ended`. Starting new work cancels the request.
The terminal row therefore never appears before the work that proves the turn
closed.

Automatic policy ends clean coordination state but do not qualify as
run-quality evidence. Verified archive ends require an independent ambiguity
review before corpus admission.

## Session-name projection

A lifecycle change is title-silent unless it marks the session done:

| Lifecycle | Suggested name |
| --- | --- |
| `active` | No title change |
| `blocked` | No title change |
| `done` | `[DONE] Agent <name> - <task>` |

The `coord.lifecycle_changed` event carries `suggested_session_name` only for
the `done` projection. Prompt context keeps reminding the agent until that name
is observed, and the display latch treats it like the first session name.
Reopening does not print another title. The title is still a projection;
editing it does not mutate lifecycle.

Declaring a task `done` does not archive its Claude Desktop sidebar entry.
The former desktop cleanup command was removed during the event-ledger
migration. Titles remain an output of lifecycle, not an input to it.

## Title surfaces

A title surface is the place a session's title lives and the way Harnery gets
a title onto it. Each surface declares one of three deliveries:

| Delivery | How the title gets there | Surfaces |
| --- | --- | --- |
| `display` | The agent prints the copyable name block and a person copies it into the client's title field. | `name-block`, the default for every client |
| `agent-tool` | The agent calls a rename tool the client gave it, and a hook confirms the call. | `t3-code`, for Claude Code and Codex sessions hosted as T3 Code threads, excluding delegated child threads |
| `direct` | Harnery's hook process calls a client command or API itself. | None yet |

Harnery resolves the surface when it mints the name, in `agents set-task`.
That command runs in the agent's shell, so it sees the client's environment.
Harnery checks the registered surfaces in order and takes the first one that
applies. The name block is checked last and always applies, so a session with
no better surface keeps the copyable block. The resolved surface id is stored
on the coordination row as `session_title_surface`, and the client's thread id
as `session_title_client_thread`. Later hooks read both from the row, because
a hook process does not always inherit the client's environment.

Cursor threads hosted in T3 Code stay on the name block. Their rename call
works, but their environment carries no `T3CODE_THREAD_ID`. Without the thread
id Harnery cannot tell that a Cursor session runs in T3, and cannot tell a
delegated child thread from a top-level one, so it would rename children whose
titles T3 already set from their brief. Cursor in T3 keeps the name block until
its environment carries the thread id.

In a T3 Code thread the agent renames its own thread instead of printing the
name block. It calls `t3_thread_update` with `action: "rename"` and the exact
owed title. While a title is owed, the pending-title gate lets that call
through, along with the tool-loading call some clients need first. At the
start of a session, PostToolUse confirms the rename only when the call succeeded and
both its input and its response carry the owed title. When the session is
marked done, the agent first reads the thread's current title with
`t3_thread_read`, which the gate also lets through, and renames the thread to
`[DONE] ` followed by that title. PostToolUse confirms a successful rename of
the session's own thread to any non-empty title that starts with `[DONE] `.
A call that regenerates the title, sets any other title, or targets another
thread confirms nothing. If the rename
tool is missing or the call fails, Harnery asks for the name block instead,
and either a confirmed rename or a correctly placed block closes the request.

A title is written at the start of a session and when the session is marked
done, and at no other time. A title minted in the middle of a session would
describe one turn of work and be too narrow to name the whole session. When a
writing surface confirms a title, Harnery records it on the row as
`session_title_applied_for`. After that, the only title change allowed is the
terminal one with `[DONE] ` prepended, and `session_title_applied_for` then
holds the done title actually written. In a T3 Code thread the done title keeps
the thread's current wording, so a title the person edited by hand during the
session only gains the prefix. This costs one extra read call when the session
is marked done. A stored name corrected after the title was applied is not
pushed to the open thread. The name block uses the corrected name when the
session is marked done.

### Adding a client

A new client needs a supported way for the agent or Harnery to set its title.
With that in place, adding it takes four changes:

1. Add one surface file in `src/core/agents/session-title/surfaces/` that
   implements `SessionTitleSurface` from `types.ts`.
2. Add one line for it to `TITLE_SURFACES` in `registry.ts`. Keep the name
   block last, since it always applies.
3. Add tests for detection, the instruction wording, and confirmation or
   fallback.
4. Add a row to the table above.

[ADR 0247](/decisions/0247-set-the-session-title-on-the-client/) records the
reasoning and the alternatives Harnery rejected.

## Live state and replay

The heartbeat projector writes these fields to `.harnery/active/<id>.json`:

```json
{
  "activity": "needs_input",
  "activity_updated_at": "2026-08-12T10:02:00.000Z",
  "activity_source": "wait.started",
  "task_state": "active",
  "task_state_updated_at": "2026-08-12T09:30:00.000Z"
}
```

Heartbeats are a live projection. The canonical event ledger is the durable
record. The public `foldSessionState()` helper rebuilds both axes from a session
slice, even after its heartbeat has been removed. Live projection and replay
call the same transition reducer. Replay orders evidence by event timestamp,
so an older event appended later cannot roll the state backward.

## Where the state appears

Harnery carries the same two labels through every operator surface:

- `harn agents whoami`, `list`, `status`, `show`, and `trace`, including JSON
- prompt-time peer context and its change-detection hash
- cross-machine presence blobs and remote peer readers
- web cards, agent chips, the agent detail page, and ended-session detail reads

The presence hash includes activity, lifecycle, and the bounded blocker reason.
A state-only change therefore reaches another machine without waiting for a task
or file claim to change. The web refresh signal also observes heartbeat writes,
so lifecycle-only updates repaint the live view.

Ended and swept heartbeats disappear from the live board. Their event-derived
identity and session state remain available to history and detail readers. This
keeps the live board honest without discarding the lifecycle record.

See [ADR 0072](/decisions/0072-event-derived-session-state/) for the decision
and rejected inference rules.
