## The ledger spans several epochs

`.harnery/ledgers/v3/active.ndjson` holds only the current epoch. When it
reaches `events.rotate_active_bytes` (32 MiB by default), Harnery moves the
whole epoch into `.harnery/ledgers/v3-archives/epoch-<stamp>/` and starts a new
one. A busy project can rotate several times a day, so reading the active file
alone shows a few hours of history. Archives are kept for
`events.archive_max_age_days` (7 by default) under `events.archive_max_bytes`
(1 GiB by default).

`harn events epochs` lists every retained epoch with its first and last event
time, event count, and size. `harn events query` reads them all as one history.

## Query

`query` lists matching events, keeping the most recent `--limit` rows (50 by
default; `0` lists all), or counts them with `--count-by`. Every result ends
with a coverage line naming how many epochs were searched and how far back the
history reaches.

| Flag | Description |
| --- | --- |
| `--since`, `--until` | Time window: `30d`, `12h`, `90m`, or an ISO date or time. Epochs that closed before `--since` are skipped without being read. |
| `--type <types...>` | Event types. Exact names, or prefixes ending in `.` or `*` (`tool.`, `coord.*`). |
| `--session <id>` | Instance id or prefix, with or without `inst_`. |
| `--tool <name>` | Tool name or command executable. Completions are joined to their opening `tool.requested` or `command.started` event within the same epoch. |
| `--outcome <outcome>` | Completion outcome, such as `succeeded` or `failed`. |
| `--count-by <field>` | `type`, `session`, `subject`, `outcome`, `day`, `hour`, or `epoch`. |
| `--tz <zone>` | IANA zone for printed times and day or hour groups. Defaults to the machine's zone. |
| `--json` | Emit rows or counts plus per-epoch summaries. |

The ledger stores commands, tool inputs, and results as fingerprints, not text,
so `query` filters on recorded structure rather than on error messages. It reads
the stored lines for inspection and does not validate authority; `latency` and
other projections keep the validating reader.

```bash
# How far back does the history go?
harn events epochs

# Which tools failed most in the last week?
harn events query --since 7d --type tool.completed --outcome failed --count-by subject

# One session's recent activity
harn events query --session 7aef7ec6 --limit 100

# Failures per day
harn events query --since 30d --outcome failed --count-by day
```

## Recover archived ready events

A cutover previously could archive durable spool rows before promotion. New
cutovers exclude publication and promotion while draining the old epoch, and
carry every queued row the writer would admit into that epoch's historical
file. Rows the writer would not admit yet, rows of a schema outside the
epoch's additive group, and files that can never be appended stay in the
archived queue with their bytes intact, so they never stop a rotation. A busy
lease, or committed history that fails validation while rows are queued, stops
the cutover before the directory moves.

Use `recover-ready` for an epoch that was already archived with stranded rows.
The command requires one exact `epoch-<stamp>` archive name. It defaults to a
dry-run that lists event IDs and types. `--max-events` bounds the number of spool
receipts inspected, with a default of 1000. `--yes` appends the validated missing
rows to that archive's `active.ndjson`. It never writes the live epoch or
changes the history reader to accept spool files.

```bash
harn events recover-ready epoch-20261104164357439 --max-events 6 --dry-run
harn events recover-ready epoch-20261104164357439 --max-events 6 --yes
```

Recovery checks canonical frames, filename digests, epoch fences, existing event
IDs, causal and producer order, attestations, and sealed-segment integrity. The
original manifest's schema digest, with every digest additive to it, sets the
accepted schemas; frames must still pass this implementation's structural
validator. Unsupported shapes, conflicts, or missing dependencies stop the
import before any rows are written. This validates historical rows and grants
no current authority.

Spool receipts stay intact as evidence. Repeating an import skips identical
event IDs already in history. After an interrupted append, recovery can repair
a partial tail only when it matches a durable ready frame. Copy an archive
to a disposable coordination root and pass `--root` to rehearse the operation.

## Latency

Read the canonical V3 ledger and project turn wall time, inclusive tool time,
exclusive command time, per-kind waits, response latency, inference, harness
overhead, residual time, context use, and token economics. The command fails
closed when the validating reader reports an incomplete ledger.

### Views

The default table shows one row per turn. `--by-tool` groups inclusive duration by tool namespace and name. `--by-generation` aggregates turns into generation totals. The two grouping flags are mutually exclusive.

### Options

| Flag | Description |
| --- | --- |
| `--root <path>` | Read coordination state from an explicit project root. |
| `--candidate` | Read the pre-activation candidate instead of active authority. |
| `--by-tool` | Aggregate inclusive latency by tool. |
| `--by-generation` | Aggregate latency by generation. |
| `--json` | Emit the complete latency and economics projections plus the selected view. |

### Examples

```bash
# One row per completed turn
harn events latency

# Inclusive tool totals
harn events latency --by-tool

# Generation totals from a candidate ledger
harn events latency --candidate --by-generation

# Full machine-readable projection
harn events latency --json
```

### Output

Observed durations render as milliseconds. Partial observations render with a
question mark and preserve known lower bounds. `ACTION` is the mixed interval
from turn start to the first tool request, or to the terminal response for an
attested no-tool turn. `POST-TOOL` is the interval from the last complete tool
terminal to turn completion. Neither field is provider inference.

JSON output includes the selected root and authority, the chosen view,
per-turn latency, and token economics. Each turn includes:

- `response_latency`, with first-action, first-tool, no-tool-terminal, and
  post-tool intervals;
- `wait_coverage_by_kind` for permission, needs-input, decision, approval,
  scheduled, rate-limit, and unknown waits; and
- `context_coverage`, which distinguishes exact, partial, unsupported, and
  missing measurements.

A turn can first report a partial context observation and later receive an
exact append-only observation when a bounded native source finishes flushing.
The projection uses the newest observation scoped to that turn.

Harnery reports a zero wait duration only when the completed turn independently
attests completeness. Delivered wait spans remain lower bounds without that
attestation. `inference_ms` stays unknown unless a native runtime field reports
provider inference duration.
