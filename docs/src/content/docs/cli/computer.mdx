```
harn computer status [--json]
harn computer install [--driver <id>] [--yes] [--json]
harn computer up [--driver <id>]
harn computer down [--driver <id>]
harn computer doctor [--driver <id>] [--json]
harn computer tools [--driver <id>]
harn computer describe <tool> [--driver <id>]
harn computer call <tool> [json] [--driver <id>] [--wait <seconds>] [--keep-screenshot]
harn computer displays [--json] [--cached]
harn computer window [--display <selector>] [--corner <corner>] [--size <WxH|smallest>] [--margin <n>] [--apps <on|off>] [--clear]
harn computer lease status [--json]
harn computer lease acquire [--wait <seconds>]
harn computer lease release
```

`harn computer` gives every harness the same desktop control through two
pinned, checksum-verified driver binaries, each called through its CLI.

Agents choose the route in three steps: what the task is, how to do it, and
how the person receives the result. They work invisibly first (vendor APIs,
CLIs, files, `harn fetch`, headless `harn browse`) and deliver in the chat: an
answer, a link that reproduces the page's state, or a picture of just the part
that matters; a page opens in the person's browser only when they ask. The
desktop is for a desktop program with no file or API route, a site that
refuses the headless browser even when signed in, or work the person will
continue in a window no link can hand them. Using the screen, changing
something in an outside system, and sending a message are three separate
approvals. An agent app's own browser, a pane built into the app or the
app's control of the person's Chrome, comes last, after every other route
failed, and is never used for a sign-in. Asking for a result is not asking
for a new tool: agents ask before writing an integration the repository
would keep. An automation-controlled headed browser window is kept for what
only Playwright provides, such as scripted batches with assertions, HAR
capture, or viewport emulation. The full routing is in the `harn-computer`
skill. The design is in
[decision record 0228](/decisions/0228-computer-use-through-a-pinned-desktop-driver/)
and [decision record 0231](/decisions/0231-two-desktop-drivers-on-every-desktop/).

## Drivers

| Id | Driver | Reads and acts through | Daemon |
|---|---|---|---|
| `cua` | Cua Driver 0.49.9 | Tool calls with element tokens; accessibility, keyboard and pixel routes; window screenshots; an isolated browser through CDP | Yes |
| `agent-desktop` | agent-desktop 1.3.1 | Accessibility-tree snapshots with refs scoped to each snapshot; headless semantic actions by default | No; on macOS it starts its own command host, which `status` reports and `down` stops |

Both drive the same desktop under the same lease. `call`, `tools` and
`describe` use one driver: `--driver <id>`, else the project's
`computer.driver`, else `cua`. `install`, `up`, `down` and `doctor` act on
every driver unless `--driver` names one.

## Enabling it

The command is inert until a project opts in with a mode:

```jsonc
// .harnery/config.jsonc
{
  "computer": { "mode": "ask-each-task" }
}
```

| Mode | Meaning |
|---|---|
| `off` | No desktop control (the default) |
| `ask-each-task` | The person approves each stated purpose; the approval lasts up to `grant_minutes` (default 20) |
| `ask-once-per-session` | One approval covers the rest of that agent's session, up to 12 hours |
| `on` | No approval needed |

`"enabled": true` without a mode still means `on`. Only the project file turns
desktop control on; a malformed or contradictory section counts as `off` and
`status` says why. Where the project is not `off`, `install`, `up`, `call`, and
`lease acquire` work, and `harn init` renders the `harn-computer` skill into
each adapter's skills directory. Optional tunables: `grant_minutes`,
`idle_seconds` (default 120), `wait_seconds` (default 30),
`foreground_quiet_seconds` (default 3), and `foreground_wait_seconds`
(default 60). See
[`computer` in the config schema](/reference/config-schema/#computer) and
[decision record 0230](/decisions/0230-desktop-control-approval-modes/).

### Each person's own mode

The project's mode is the default. Where the project is not `off`, each person
may choose their own with `harn computer mode <mode>` (this project) or
`--all-projects`, and remove it with `--clear`. The choice is stored in
`computer.json` beside the user config (`~/.config/harnery/`), never in the
project, so committed files do not change. A personal mode never turns on a
project that is `off`. Loosening it shows the person a Yes/No prompt first;
tightening does not.

### Agent sign-in

By default the person signs in to websites themselves, and the
`harn-computer` skill tells agents never to type a password, username or
one-time code. A project can let each person change that:

```jsonc
// .harnery/config.jsonc
{
  "computer": { "mode": "ask-each-task", "sign_in": true }
}
```

Each person's choice still starts off. `harn computer sign-in on` (this
project, or `--all-projects`) turns it on after a Yes/No prompt; `off` turns
it off and `--clear` removes the choice. It is stored in `computer.json`
beside the mode. `status` shows a `sign-in:` line, and with it on the skill
tells agents to sign in in the person's running browser (or a
`browse --login --detach` window) by choosing the matching login in their
password manager's browser extension, never typing it. A locked password
manager, a passkey, a hardware key, a system prompt, or a code sent by email
or text still goes to the person, and agents never sign in inside an
isolated or automation-controlled browser. A person whose own mode is `off`
gets no agent sign-in either; a saved `on` then shows as inactive (JSON
`person_sign_in: true` with `sign_in: false`), comes back with desktop
control, and can still be turned off.

### Browser attach

Cua can attach to the person's running Chrome, Edge or Brave and act inside
its tabs (read a page, navigate, type, click) without moving their mouse or
bringing the window forward. The driver allows that only when its daemon
was started with a grant, and the grant covers every agent on the machine
while that daemon runs, so it is off unless both the project and the person
turn it on:

```jsonc
// .harnery/config.jsonc
{
  "computer": { "mode": "on", "browser_attach": true }
}
```

`harn computer browser-attach on` (this project, or `--all-projects`) turns
it on after a Yes/No prompt; `off` and `--clear` work as for sign-in, and the
choice is stored in `computer.json`. Changing it restarts a running Cua
daemon with or without the grant, unless another agent holds the desktop.
`status` shows a `browser:` line, and the daemon line says when the running
daemon can attach.

`call` refuses a `browser_prepare` with `strategy: {"kind": "existing_profile"}`
(directly, as a nested step, or in a `run_script` program) with exit 4 while
browser attach is off. With it on, `call` restarts a daemon that lacks the
grant before sending the attach, and treats the attach as a foreground action:
its one-time setup brings the browser forward and answers the browser's
consent prompt, so it waits for a quiet keyboard and mouse first. Browser
attach and agent sign-in are separate: the browser tools never sign in. See
[decision record 0249](/decisions/0249-attach-to-the-persons-running-browser/).

#### Own window

An agent works in a window of its own. `harn computer browser open` opens a
new window in the person's browser and binds it, and `harn computer browser
close` closes it again (see [below](#computer-browser-open--close)). `call`
then checks every browser tool call against that window and refuses, with
exit 4 and nothing sent, a call that could act on the person's own tabs or
their secrets:

| Code | Refused call |
|---|---|
| `browser_window_not_yours` | An attach to, or a bind of, a window of the person's attached browser that the agent did not open. `--person-window` overrides it, only when the person asked the agent to work in a window they opened; the override is logged |
| `browser_target_unknown` | A browser tool call whose target the agent did not bind. The driver mints new `target_id` and `tab_id` values on every bind, so use the ones from the latest bind |
| `browser_sensitive_field` | `browser_type` into a field that takes a password, passcode or one-time code, matched by the field's name or its `type=password` attribute |
| `browser_read_back_required` | `browser_click` or `browser_pointer` in a tab after `browser_type`, without a newer `get_browser_state` snapshot of that tab |
| `browser_password_offer` | A click while the latest snapshot shows a password manager's save or fill offer |
| `browser_script_not_checked` | A `run_script` program that names browser tools, or the legacy `page` tool. Make each browser call its own call |

The typing and click rules also cover the tabs of a driver-owned isolated
browser. The guard is cooperative: a client that talks to the daemon
directly skips it. Field and offer detection are heuristics, and they let a
call through when its element reference is not in the latest snapshot. See
[decision record 0250](/decisions/0250-keep-agents-in-their-own-browser-window/).

### Agent window placement

An agent's own windows open out of the person's way. By default a window
opens at the smallest size the program allows, in the bottom-right corner of
the secondary display: the first display that is not primary, counting left
to right, or the only display on a one-display desktop. `computer browser
open` places its window this way, and a program an agent launches through a
driver's launch tool has its windows moved to the same corner at their own
size, cut down only when they cannot fit on that display. A project sets its
default:

```jsonc
// .harnery/config.jsonc
{
  "computer": {
    "agent_window": {
      "display": "secondary",
      "corner": "bottom-right",
      "width": 900,
      "height": 700,
      "margin": 0,
      "move_apps": true
    }
  }
}
```

| Field | Default | Meaning |
|---|---|---|
| `display` | `secondary` | `secondary`, `primary`, a 1-based number counting left to right then top to bottom, or a display id or name from `computer displays` |
| `corner` | `bottom-right` | `top-left`, `top-right`, `bottom-left` or `bottom-right` of the display's work area |
| `width`, `height` | smallest | Window size in pixels. Without them the window takes the smallest size the program allows |
| `margin` | `0` | Gap in pixels between the window and the corner |
| `move_apps` | `true` | Also move the windows of programs an agent launches through a driver's launch tool |

Every field is optional. Displays belong to the machine, so each person may
set their own placement for every project:

```bash
harn computer window --display 2 --corner top-right --size smallest
harn computer window --apps off
harn computer window --clear
harn computer window
```

The person's fields win over the project's, field by field. With no option
the command shows the effective placement and where each field came from.

Placement never fails a command. With no displays read, no driver that can
move windows, or a display that is not connected, the window stays where the
system put it and one line says why. A small window can make a responsive
page show its narrow layout, so element names can differ from the wide
layout. Agents never minimize their window: the driver refuses reads and
actions in a minimized window. See
[decision record 0251](/decisions/0251-place-agent-windows-on-a-chosen-display/).

## Approval

In an ask mode, `call` and `lease acquire` refuse with exit 4 until the agent
holds an approval:

```bash
harn computer grant --purpose "export the October invoices from the accounting app"
harn computer call ...
harn computer done
```

`grant` asks the person directly: a Yes/No prompt in an interactive terminal,
or otherwise a native dialog on the desktop (Windows, also from WSL; macOS;
Linux desktops with `zenity`). The dialog names the agent, the project it is
working in, and its purpose, says how long the approval lasts, and reminds the
person to close anything the agent should not see, because whatever is on
screen can reach the model provider. It defaults to the refusing button, and no
answer within `--timeout` (default 120 seconds) counts as no. `done` ends a task
approval and releases the desktop; `lease release` also ends it. `revoke` ends
your approvals now, and `revoke --all` ends every agent's on this desktop.

An approval belongs to one agent in one project. An agent that points
`HARNERY_COORD_ROOT_OVERRIDE` at another project is still named by its own
session: Harnery finds that session in the project that registered it, so the
dialog, the approval and the lease show the agent's name, and the approval is
kept for the project the command acts on. Only a caller outside any agent
session is named after the operating-system user (`shell-<user>`), and every
such shell by that user shares one approval and one lease.

Approvals and every decision about them are kept beside the lease
(`grants.json` and `grants-log.ndjson`). They are plain files any process
running as the desktop's user can write, so an approval is a cooperative check
that stops a well-meaning agent acting unasked. It is not a security boundary
against an agent that sets out to get around it.

## Platforms

| Host | Status |
|---|---|
| Windows 10/11 (native) | Both drivers. State in `%LOCALAPPDATA%\harnery` |
| WSL2 on Windows 10/11 | Both drivers' Windows builds, run through interop to drive the Windows desktop; same state directory |
| macOS 13+ | Both drivers. State in `~/Library/Application Support/harnery`. Cua Driver runs from `/Applications/CuaDriver.app`. Each needs a one-time Accessibility (and Screen Recording) grant |
| Linux desktop | Both drivers. State in `$XDG_STATE_HOME/harnery` (default `~/.local/state/harnery`). Run inside the signed-in user's graphical session with `at-spi2-core` |

## computer status

```bash
harn computer status
```

Shows whether the project enables computer use, the host kind, and for each
driver its pinned version, whether it is the default, the installed executable
(or `not installed`), and whether its daemon is running (or not needed). A
driver that leaves background processes running after a call, such as
agent-desktop's command host on macOS, gets a `helpers:` line with their
process ids. It ends with the current desktop lease holder, its generation,
and its idle expiry. `--json` emits the same fields, with the drivers under
`drivers` (background processes under `background_processes`) and the default
under `default_driver`. It also lists agent browser windows that are still
open. Status never changes anything.

## computer install

```bash
harn computer install                                # preview both drivers
harn computer install --yes                          # install both
harn computer install --driver agent-desktop --yes   # install one
```

Without `--yes` it prints each plan only: URL, SHA-256, install directory,
executable, any preference file, any further step, and any one-time setup the
person must do. With `--yes` it downloads each pinned archive (`.zip` or
`.tar.gz`), checks its SHA-256, extracts it to a versioned directory under the
desktop's shared state directory, and writes Cua Driver's preference file
(telemetry off) before that binary first runs. On macOS it then verifies
`CuaDriver.app` with `codesign --verify --deep --strict`, checks its bundle
identifier, and copies it to `/Applications`, replacing only an older Cua
Driver bundle. It never edits `PATH`, registers autostart, or elevates.
Re-running is idempotent. One driver failing does not stop the other; the
command then exits 1. Upgrading a driver is a Harnery release that moves its
pin.

## computer up / down

`up` starts each installed driver's daemon at the user's normal integrity level
if it is not already running. `down` stops them, together with any background
processes a driver left running. agent-desktop has no daemon, so `up` skips it;
on macOS `down` stops its command hosts, one per calling environment, which it
otherwise keeps running after each call. While another agent holds the desktop,
`down` leaves those processes alone, because a call may be using them, and
exits 3. `call` starts a needed daemon on its own, so `up` is optional.

## computer doctor

Runs each installed driver's own health report and prints one line per check
under the driver's name. agent-desktop's checks are its OS permission states,
so a missing macOS Accessibility grant shows here, naming the app the grant
belongs to: macOS charges agent-desktop's requests to the app it runs inside
(a terminal, an editor, an agent app), and each such app needs its own grant.
Automation reads as information, since macOS asks for it per target app only
when an action needs it. Until Cua Driver's grants apply on macOS, its daemon
answers everything with `permissions_pending`; doctor turns that, and a daemon
that is not running, into a failing check that says what to do. A new grant
can take about a minute to apply. Any check that does not pass, or a failing
driver exit, exits 1. `--json` emits
`{ ok, drivers: [{ driver, ok, exit_code, checks, report }] }`.

## computer tools / describe

`tools` lists one driver's tools. `describe <tool>` prints one tool's full
description and arguments. Agents look up a schema on demand instead of
carrying the whole catalog in every turn. For agent-desktop, `describe` adds
the JSON keys the command accepts, and `describe skill:desktop` (or
`skill:platform`) prints the binary's own guide for its version.

## computer call

```bash
harn computer call launch_app '{"name": "notepad"}'
harn computer call get_window_state '{"include_screenshot": false}'
harn computer call get_window_state '{"screenshot_out_file": "/tmp/state.png"}'
harn computer call --driver agent-desktop snapshot '{"app": "Notepad.exe", "interactive_only": true}'
harn computer call --driver agent-desktop set-value '{"ref_id": "@s8f3k2p9:e1", "value": "hi"}'
```

Runs one tool call and prints the driver's JSON. For agent-desktop the tool is
a command name and the JSON keys are that command's snake_case field names;
Harnery runs it as a one-entry `batch` and prints the command's own envelope,
exiting 1 when its `ok` is false. `"headed": true` moves to the global
`--headed` flag. The tool `batch` with `{"commands": [...]}` runs several
entries in one process. The arguments must be a JSON
object (default `{}`). In order, the command:

1. Sets `session` to the caller's agent name when the arguments omit it, so
   the driver's per-session state follows the agent. A shell outside any agent
   session is labelled `shell-<user>`.
2. Takes the desktop lease for the caller, or refreshes it. When another agent
   holds it, the call waits up to `--wait` seconds (default `wait_seconds`,
   else 30) and then exits 3:

   ```
   Desktop is held by agent-Ada (generation 7, idle-expires in 84s). Wait, or ask them to run `harn computer lease release`.
   ```

   When the caller newly takes the lease, at the start of a stretch of
   computer use, Harnery reads the [displays](#computer-displays) fresh, so
   window placement never works from a stale layout.
3. Starts the driver's daemon if it has one and it is not running. An
   attach to the person's running browser is refused (exit 4) unless
   [browser attach](#browser-attach) is on, and with it on a daemon without
   the grant is restarted first. A running daemon whose version is not the
   pinned one is restarted too (`up` does the same), so an upgrade never
   leaves the old daemon serving the new client. The browser guard
   ([own window](#own-window)) checks the call here.
4. Holds a [foreground action](#foreground-actions-wait-for-the-person) until
   the person's keyboard and mouse are quiet, or exits 5 with nothing sent.
5. Translates file paths in the arguments and results between WSL and Windows
   syntax, so `screenshot_out_file` or `output_path` can name a WSL path.
6. Replaces the value of any key ending in `png_b64`, and any other string of
   2,048 or more base64 characters, with a short `<omitted N chars; …>` note,
   so one state read cannot flood an agent's context. Pass `--keep-screenshot`
   to keep the inline image, or write it to a file and read that file.
7. Starts a named driver session again when the driver rejects it. Cua ends
   a session after 5 minutes idle and then rejects calls that name it, so
   `call` starts it again and retries once, and the agent sees no error. An
   idle browser attach therefore closes itself after 5 minutes.

The driver's stderr passes through and its exit code becomes the command's
exit code.

### Foreground actions wait for the person

Most calls work in the background: the driver presses a control through the
accessibility tree and no window comes to the front. Some targets ignore that
kind of input, and the driver then needs a foreground action, which brings the
agent's window to the front and sends real keyboard and mouse input. While it
runs, anything the person types lands in the agent's window.

So `call` reads how long the person's keyboard and mouse have been quiet
before it sends one. If that is at least `foreground_quiet_seconds` (default
3), the action goes at once. Otherwise the call waits, for up to
`foreground_wait_seconds` (default 60), and then refuses:

```
The person is using the keyboard or mouse, so this foreground action was not sent (waited 60s for 3s of quiet).
```

That refusal exits 5 and sends nothing to the driver. The agent keeps the
lease and should try once more later. Background actions never wait.

| Driver | Counts as a foreground action |
|---|---|
| cua | `delivery_mode: "foreground"` on the call or on any step of `run_steps`; `run_steps` with `foreground_fallback: true`; `bring_to_front`; `browser_prepare` with `strategy: {"kind": "existing_profile"}`, directly or nested; a `run_script` program that names any of them |
| agent-desktop | `"headed": true`; `"activate": true` on a launch; `focus-window`; any of those inside a `batch` |

The reading comes from the operating system: Windows (also from WSL) and
macOS always give one, and an X11 Linux desktop gives one when `xprintidle`
is installed. A host with no reading sends the action without waiting. The
systems count an agent's own foreground input as input, so two foreground
actions in a row are at least one quiet period apart. Set
`foreground_quiet_seconds` to `0` on a machine nobody else types on.
`status` shows the setting on its `quiet:` line. See
[decision record 0248](/decisions/0248-hold-foreground-actions-until-the-person-is-quiet/).

## computer browser open / close

```bash
harn computer browser open https://example.com
harn computer browser open --browser-pid 4120 --json
harn computer browser close
```

`browser open [url]` needs [browser attach](#browser-attach) on. It waits for
a quiet keyboard and mouse, opens a new window in the person's default
browser when it is a running Chromium browser (Chrome, Edge or Brave), else
their front-most one (`--browser-pid` picks one). It reads the displays
fresh and [places the window](#agent-window-placement) in two steps around
the attach. It first moves the window onto the target display at the size it
opened with, then attaches, and only then sizes it, reads the frame back and
positions it in the corner. The browser's own attach setup opens a page in
that window and did not finish in a window already at its minimum size. It
then binds the window, choosing the tab that shows the requested page, and
prints `pid`, `window_id`, `session`, `target_id` and `tab_id`, with the
display and the final frame. The agent then passes those ids to the driver's
browser tools (`get_browser_state`, `browser_navigate`, `browser_type`,
`browser_click`) through `call`. `--json` prints them as one object.

`browser close` ends the agent's driver browser sessions, which closes the
browser's debugging connection, and closes the windows the agent opened.
`computer done` and `computer lease release` do the same automatically. On
Windows (also from WSL) the window closes. On macOS and Linux it stays open
and the command names it, so the agent tells the person. A window opened by
an agent that has gone away stays open until that agent runs
`browser close` or the person closes it; `status` lists it.

## computer displays

```bash
harn computer displays
harn computer displays --json
harn computer displays --cached
```

Reads the desktop's displays and prints one line each: its id, its name when
the system gives one, whether it is primary, its bounds, its work area (the
display minus the taskbar, dock or menu bar, where the system reports it)
and its scale. Bounds and work areas use the same coordinate space as window
frames. On Windows, also from WSL, it runs a system query. On macOS and Linux
it asks the desktop driver for its display listing first, then falls back to
a system query (`NSScreen` through `osascript` on macOS, `xrandr` on Linux).

Each reading is cached. `--cached` prints the last reading without reading
again, and `status` shows it with its age. Harnery reads the displays fresh
when an agent newly takes the desktop lease and every time it opens an agent
window, rather than on every call, because a system query can take most of a
second under WSL. macOS and Linux queries are not yet verified on real
machines.

## computer window

```bash
harn computer window
harn computer window --display secondary --corner bottom-right --size smallest
harn computer window --size 900x700 --margin 16 --apps off
harn computer window --clear
```

Shows or sets this person's [agent window placement](#agent-window-placement)
for every project. `--display` takes `secondary`, `primary`, a 1-based
number, or a display id or name; `--corner` takes `top-left`, `top-right`,
`bottom-left` or `bottom-right`; `--size` takes `WxH` or `smallest`;
`--margin` takes pixels; `--apps on|off` sets whether launched programs are
moved too. Options set only the fields they name. `--clear` removes the
person's placement, so the project's applies again. With no option it shows
the effective placement and, for each field, whether it came from the
person, the project or the default. The choice is stored in `computer.json`
beside the user config.

## computer lease

| Command | Effect |
|---|---|
| `lease status [--json]` | Show the holder, its generation, and its idle expiry, or `free` |
| `lease acquire [--wait <seconds>]` | Take or refresh the lease without calling a tool (default wait 0) |
| `lease release` | Release the lease if you hold it and end your task approval; exits 3 when another agent holds it |

The lease is one file per desktop, kept in the desktop's own state directory,
so callers in WSL distros, native Windows shells, and different repositories
all see the same holder. An idle lease expires `idle_seconds` after the last
call (default 120). While a call runs, the lease is held for at least that
call's timeout plus a margin, so a slow call never outlives it. agent-desktop
calls time out after 30 seconds plus whatever the call asks to wait for
(`wait_timeout`, `timeout_ms`, or the `wait` command's `ms`); on macOS a
timed-out call also restarts the command host, so one unresponsive app does not
stall every later call. Each new
holder increments the generation.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | Error: computer use disabled, unsupported host, driver not installed, bad arguments, or a failing health check |
| 3 | The desktop lease is held by another agent |
| 4 | Desktop control needs the person's approval first, or they declined or did not answer, or a browser call was refused (browser attach off, or a [browser guard code](#own-window)) |
| 5 | A foreground action was held back because the person is using the keyboard or mouse; nothing was sent |
| other | `call`, `tools`, and `describe` pass through the driver's exit code |
