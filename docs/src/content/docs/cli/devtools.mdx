```
harn devtools [--tool <name>] [--usage] [--window-days <n>] [--no-api] [--format table|json]
harn devtools doctor [--tool <name>] [--format table|json]
```

Reports, in one place, every Claude Code, Codex and Cursor account signed in
anywhere on this machine, and each account's plan usage: the 5-hour and weekly
windows, Cursor's billing-cycle percentages, extra-usage or on-demand spend and
Codex credits. It also shows each tool's session count, last activity and
windowed token total.

Token strings are never printed or written to the report. Harnery reads access
tokens only and never refreshes one, because a refresh token rotates on use and
refreshing it would sign out every running session still holding the old one
([ADR 0273](/decisions/0273-usage-from-every-signed-in-account/)).

## Where accounts come from

Discovery reads files only, with no network call:

| Tool | Stores |
| --- | --- |
| Claude Code | `$CLAUDE_CONFIG_DIR`, `~/.claude`, every `~/.claude*` directory holding `.credentials.json`, and on macOS the Keychain item Claude Code writes (best effort). Email and account id come from the store's `.claude.json` (`~/.claude.json` for the default directory). |
| Codex | `$CODEX_HOME`, `~/.codex`, every `~/.codex*` directory holding `auth.json`. Identity comes from the `id_token` claims and `account_id`. |
| Cursor | The CLI's `~/.config/cursor/auth.json` (a JWT) and the IDE's `state.vscdb`. The IDE token is opaque; the user id comes from `cursorAuth/cachedScopedProfile`. |
| CLI Proxy API | `claude-*.json` and `codex-*.json` in `~/.cli-proxy-api` and in the `auth-dir` its `config.yaml` names. |

Under WSL the same places under each `/mnt/c/Users/<name>/` are read too, but
only when the reader runs against the real home directory. Session counts and
token totals still come from the Linux side.

Copies of one account are grouped: same account id where the store records one,
else same email and organization. The report shows one row per account and lists
every store it was found in, so a signed-out `~/.claude` next to a signed-in
`~/.claude_work` for the same login never hides the live one.

## Where usage comes from

For each account, `devtools` tries these sources in order and stops at the first
that answers. The account's `source` field names it.

1. **`direct`**: the vendor's usage endpoint with a stored access token that has
   not expired. The account's own stores come first, then CLI Proxy's copy.
   Claude calls `api.anthropic.com/api/oauth/usage`; Codex calls
   `chatgpt.com/backend-api/wham/usage` with `ChatGPT-Account-Id`; Cursor calls
   `api2.cursor.sh` `DashboardService/GetCurrentPeriodUsage` with a bearer token
   (CLI token first), then cursor.com's dashboard route with the session cookie.
2. **`codex-app-server`** (Codex only): `codex app-server` with `CODEX_HOME` set
   to the account's store, asked `account/rateLimits/read` over JSON-RPC. Codex
   refreshes its own token here with its own code.
3. **`cliproxy`**: CLI Proxy's management `api-call`, which makes the vendor
   request with the token the proxy holds for that account.
4. **`snapshot`** (Codex only): the rate limits the newest local session
   recorded, shown with its time and marked `stale`. A last-known-good cached
   answer is used instead when it is newer.

Every source that failed before the one that answered leaves a note on the
account, such as `direct (claude-dir …): token expired, skipped`.

### Resets and recent usage

Each account also lists `resets[]`, the limit resets it can still apply: a
`kind` (`full` clears the 5-hour and weekly windows; `fable` refills the 5-hour
window and gives back that model's weekly use), the vendor's `label`, `left`,
`total` and `expiresAt`. `null` means unknown and `[]` means none. Claude reads
them in the same usage call (`oauth/usage?cedar_ember=1`). Codex reads
`wham/rate-limit-reset-credits` after a successful usage read, through the same
route; if that fails, the usage response's count stands in without dates.

Live reads also append to a local history,
`~/.cache/harnery/devtools/history.jsonl` (a new line per limit only when its
value changed or ten minutes passed; pruned after 35 days). Each quota window,
and each of Cursor's percentages (`usage.recent.total|api|auto`), then carries
`recent`: up to 24 `[time, used]` points from the current window over a
lookback (90 minutes for 5-hour, a day for weekly, three days for monthly) and
`ratePerHour`, or null until the points span a fifth of the lookback. The Tools
page uses it for pace and the trend line, and marks the account with the most
room left as "use next".

### Configuring CLI Proxy

The management API needs the server address and its management key. They are
read from, in order:

1. `HARNERY_CLIPROXY_URL` and `HARNERY_CLIPROXY_KEY`;
2. `~/.config/harnery/cliproxy.json` (or under `XDG_CONFIG_HOME`):
   `{ "url": "http://127.0.0.1:8317", "key": "…" }`;
3. a desktop agent app's saved usage-limit source of kind `cliproxy`, when one
   is found under `~/.t3/userdata/` (or the Windows-side copy under WSL).

CLI Proxy stores its own management key hashed, so the key must come from one
of these. Under WSL a `127.0.0.1` address saved on the Windows side is
unreachable from Linux, so the Windows host's address (the default gateway)
is tried as well. The key is sent only to the configured server.

### Rate-limit discipline

These endpoints are shared with the tools' own clients, and Anthropic's
`oauth/usage` is sharply rate-limited. So:

- **Cached per token for five minutes** under `~/.cache/harnery/devtools/`. A
  machine with four accounts makes at most four usage calls per tool per five
  minutes, however often the dashboard re-renders.
- **Backs off on a 429.** A rate-limited answer arms a cooldown from
  `Retry-After` and suppresses calls until it passes; the chain moves to the
  next source meanwhile.
- **Requests carry the tool's own client identity.** Claude sends
  `claude-cli/<version> (external, cli)` + `x-app: cli` with the version the
  running client stamps into its newest transcript; Cursor sends its Electron
  client UA with the version from `state.vscdb`.

### Checking for drift

The vendor endpoints are undocumented, so a client update can change the
required headers or the response schema. `harn devtools doctor` probes each
source once per tool (bypassing the cache): the direct endpoint with the first
usable token, `codex app-server`, and the CLI Proxy management API.

```
✓ claude-code  direct            ok             200, expected shape present
   https://api.anthropic.com/api/oauth/usage  (client 2.1.207)
✓ claude-code  cliproxy          ok             200 via CLI Proxy
✓ codex        direct            ok             200, expected shape present
✓ codex        codex-app-server  ok             answered for /home/you/.codex
✓ codex        cliproxy          ok             200 via CLI Proxy
✓ cursor       direct            ok             200, expected shape present
```

`auth_rejected` (401/403) means our headers or token stopped being accepted;
`shape_changed` means a 200 came back without the fields we parse. Either is the
signal to review the request builder or the parser. `rate_limited` and
`no_credential` are not defects. Run it by hand; it is not scheduled.

## Options

| Flag | Effect |
| --- | --- |
| `--tool <name>` | Restrict to a tool (repeatable): `claude-code`, `codex`, `cursor`. Default: all three. |
| `--usage` | Force a fresh, cache-bypassing recount of Claude Code's token total (the card already shows it, memoized). |
| `--window-days <n>` | Window for token totals: only count transcripts / rollouts modified within N days (default 7). |
| `--no-api` | Skip every network source; accounts show local data only (Codex keeps its snapshot). |
| `--format <type>` | `table` (default) or `json`. |

## Token totals

Codex's total is each in-window session's cumulative `total_token_usage` (the
last `token_count` event in its rollout), so it costs one bounded tail-read per
rollout. Claude Code's total sums every message of every in-window transcript
across the Claude config directories, memoized per transcript at
`~/.cache/harnery/devtools/claude-tokens.json` (keyed by path, mtime and size)
so only changed transcripts are re-read. Both include cache tokens, so expect a
number far larger than the billed count. Cursor keeps token counts server-side.

## Cursor Cloud Agents (needs an API key)

If you store a Cursor API key, the Cursor entry also gains
`api: { ok, keyName, cloudAgents }` from the public `/v0` API:

```
harn devtools cursor-key set          # paste the key on stdin
harn devtools cursor-key status       # is a key configured, and from where
harn devtools cursor-key clear        # remove it
```

The key is read from `CURSOR_API_KEY` first, then `~/.config/harnery/cursor-api-key`
(stored `0600`). Cursor's public usage API is Team-only, so the key only adds
Cloud Agent runs; billing numbers come from the account sources above.

```
       quota (5h)   4% used · resets 2026-07-13T11:10:00Z

```

The JSON envelope is `{ ok, generatedAt, windowDays, tools: ToolStatus[] }`.
Each `ToolStatus` carries `installed`, `loggedIn`, `sessions`, `lastActivity`,
`tokensUsed`, `api`, `notes[]` and `accounts[]`; its `account`, `plan`,
`rateLimitTier`, `authExpiresAt`, `quota`, `usage` and `spend` describe the first
signed-in account. Each account carries `id`, `email`, `org`, `plan`,
`rateLimitTier`, `loggedIn`, `authExpiresAt`, `stores[]` (`kind`, `path`,
`loggedIn`, `authExpiresAt`), `source`, `sourceDetail`, `stale`, `asOf`,
`quota[]`, `usage`, `spend`, `credits`, `resets[]` and `notes[]`.

## Helper agents

A helper agent is an agent another agent starts for part of its work, such as
a Claude Code subagent or a `harn run` worker. Helpers can cost as much as the
main session. The helper limit sets the most expensive model and the highest
effort a helper may use. A helper asked for more is lowered to the limit. A
helper asked for less, or one that names no model or effort, is left alone.

```bash
harn devtools helpers                  # the limit, whether it is active, the last 24 hours
harn devtools helpers opus medium      # set your limit for all your projects
harn devtools helpers sonnet           # model only; effort has no limit
harn devtools helpers medium           # effort only; model has no limit
harn devtools helpers none             # no limit, even where a project sets one
harn devtools helpers --clear          # remove your choice so the project default applies
harn devtools helpers --install        # install or refresh the Claude Code plugin
harn devtools helpers --uninstall      # remove the plugin
harn devtools helpers --format json    # the same report as JSON
```

The words can come in any order. Setting a limit replaces the whole pair: `sonnet`
alone removes an effort you set before. Models, cheapest first, are `haiku`,
`sonnet`, `opus` and `fable`. Efforts, lowest first, are `low`, `medium`,
`high`, `xhigh` and `max`. The dashboard's Tools page offers the same choice.

### Where the choice is stored

Your choice covers every project on this machine. It is kept in
`~/.config/harnery/preferences.json` (or under `XDG_CONFIG_HOME`). A project can
commit a default in `.harnery/config.jsonc`:

```jsonc
{ "helpers": { "claude-code": { "max_model": "sonnet", "max_effort": "medium" } } }
```

Your choice wins over the project default in both directions. When you have
made no choice, the project default applies. When neither is set, helpers have
no limit.

### How it is applied

A small Claude Code plugin applies the limit to each helper's request to the
model. Setting a limit installs it, and `--install` refreshes it. Claude Code
sessions that are already open need a restart to pick it up. Harnery starts
`harn run` workers itself, so it applies the limit to them directly.

The limit applies to Claude Code helpers, including helpers started by helpers
and Workflow agents, and to `harn run` workers on Claude Code. It does not
apply to forks, to agent-team teammates, or to helpers in Codex, Cursor and
OpenCode.

If the limit falls below a full-access floor configured for run workers, those
workers run sandboxed, and the report says so.

Every helper is counted in a machine-wide log under `~/.cache/harnery/helpers/`,
kept seven days, even with no limit set. The report shows how many helpers ran
in the last 24 hours, how many were lowered and which models they ran on.

The limit is a best-effort cost preference, not a guarantee. When Harnery
cannot apply it, for example on an older Claude Code or without the plugin,
helpers run as asked and the report says the limit is not active.
