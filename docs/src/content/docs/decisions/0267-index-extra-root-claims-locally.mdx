**Status:** accepted (2026-11-14) · **Scope:** product tier (`core/agents/finalization`, `core/agents/live-authority-v3`, `core/agents/state/finalization-path-index`, session-end cleanup in `core/hooks`)

## Context

A host can list extra Git repositories in `agents.finalizationRoots`, and
sessions may claim and edit files there. The V3 contract records a claim on a
path outside the coordination repository as an `external_path` target with a
fingerprint and no path, so absolute paths from one machine never enter a
ledger that other machines read. The coordination view lists only workspace
paths, so the end-turn check, Stop's supplemental check and `agents lifecycle
done` never saw these claims. A session could leave a dirty or unpushed file
in an extra root and still finish. ADR 0264 found the gap while fixing released
claims in the coordination repository and left two tests marking it.

## Alternatives considered

- **Add a display path to `external_path` targets inside configured roots.**
  Rejected. Readers on older builds validate targets strictly and would reject
  the new field, which fails the shared ledger closed for every session until
  every reader upgrades. It would also put one machine's absolute paths into a
  ledger shared across machines, where they mean nothing and expose local
  layout.
- **Read the claim path back from the heartbeat cache.** Rejected. The cache
  holds only paths held now, so released claims would still vanish, and it is
  rebuilt from the ledger, which has no path to give it.

## Decision

Keep a machine-local index of these claims. When a session acquires a write
claim whose canonical path is absolute and classifies into a configured `git`
finalization root, Harnery records an entry in
`.harnery/finalization-paths/<instance>.json`: the session generation, the
canonical path, the configured root, the ledger target fingerprint when the
acquisition recorded one, and the state `held`. A release marks the entry
`released`; claiming the path again marks it `held`. Every claim change already
passes through one recording function, so the index is maintained there.

The finalization read merges the current generation's entries into the
session's scope: held entries join the held paths (dirty-file and push
obligations), released entries join the repository-only paths (push
obligations, as in ADR 0264). The existing check then classifies and inspects
them like any other path.

Edge cases:

- **Root without a remote.** Dirty files still refuse; commits owe no push,
  matching the rule for any repository without a remote.
- **Root removed from the configuration.** A held path is named as outside the
  finalization roots, as before. A released path outside the coordination
  repository that no longer classifies is now named too, instead of passing.
- **Path outside every root.** Not indexed. The write guard already refuses
  such claims where Git finalization is required.
- **Missing index.** Nothing is added, which is the earlier behavior.
- **Unreadable index.** The claim history counts as unverified and the check
  refuses. The message names the file and the command that clears it:
  `rm --root <coordination root> --allow-protected
  .harnery/finalization-paths/<instance>.json <same path> --yes`. The guarded
  remove refuses all other live `.harnery` state; it accepts this one file,
  named exactly, because the index is derived and grants nothing. Removing it
  drops the claims it recorded from the check, so the message asks the agent
  to commit and push its extra-root changes first. The next claim starts a
  new file.
- **New claim meets an unreadable index.** The claim is recorded, but the
  index write refuses to replace the file. Replacing it would silently drop
  released entries and turn the read's refusal into a pass. The refusal stays
  until the agent clears the file as above, so it cannot strand the session.

The index grants nothing. The edit and commit guards do not read it, so it can
never block a peer. No event contract or schema changes.

## Gotchas

- Entries are keyed by instance and generation. Writes drop other generations,
  session end removes the instance's file, and any write prunes files nobody has
  written for seven days.
- Writes take a per-file lock directory and replace the file through
  temp-then-rename, so several agents on one machine cannot interleave.
- Index maintenance is best effort. A failed index write never undoes a
  recorded claim; the claim then stays invisible to the check, as before.
  This stays open: making the claim fail with the index would let a full
  disk or a held lock block every edit in extra roots, and recording a
  separate failure marker would need another file that can fail the same way.
  A write that fails while the file is readable is rare (lock wait or disk
  error), and the next successful write for the same path repairs it.
- A claim made on one machine is checked only on that machine. Sessions do not
  move between machines, so this matches where the obligation lives.
- `agents handoff` does not cover extra-root paths. The V3 contract requires
  a handoff target to be a workspace path, so the ledger refuses an offer of
  any other path. The command now refuses it first with
  `path_outside_repository` and names the route that works today: the sender
  releases the path (`agents release-claim`), which keeps only its push
  obligation in the index, and the receiver claims it, which indexes it as
  held for the receiver. Unlike a handoff, nothing waits for the receiver to
  accept, so the sender should release only after the receiver agrees to take
  the file. Supporting a real handoff here needs a contract change allowing
  `external_path` handoff targets matched by fingerprint; that is left for a
  separate decision.
