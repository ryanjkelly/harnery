---
"harnery": minor
---

Background daemons now restart when the installed Harnery code changes. Before, the presence relay client, the semantic reader and the local supervisor kept running the code they started with, so a fix that arrived by a pull or an upgrade had no effect until someone killed the old process by hand.

Each daemon now records which code it loaded: the package version, plus the checkout's HEAD commit when Harnery runs from a Git checkout. The commit is read from files, with no `git` process started. About every 30 seconds the daemon checks again. When two checks in a row see the same new code, it logs `code changed (old -> new); exiting for restart`, finishes its current work (the semantic reader completes its current model call; the relay closes its socket), and starts a replacement from the new code. A daemon whose code identity cannot be read never restarts for this reason, and a daemon stopped with its stop command does not restart.

The launchers also replace a live daemon that runs older code: `ensureRelayDaemon`, which the session hooks call, plus `ensureSemanticServiceRunning` and `ensureSupervisorRunning`. A daemon started before this release carries no code identity and cannot be asked to hand over, so the launchers leave it running until it exits on its own; restart it once with its stop and start commands to pick up the new code sooner. `ensureSemanticServiceRunning` and `ensureSupervisorRunning` can now return the state `"replaced"`, and `ensureRelayDaemon` now returns its outcome instead of nothing, including `"pending"` while another launch is already under way. A launcher never signals a daemon to replace it: it asks the daemon to hand over after its current model call or cycle, never writes or removes a stop or pause, and starts nothing while one exists. A relay daemon now holds an operating-system lock (a named pipe on Windows, a Unix socket elsewhere) for as long as it runs and connects only while holding it, so at most one relay daemon per project is connected; a replacement connects only after the daemon it replaces has exited, and a duplicate launch exits on its own.
